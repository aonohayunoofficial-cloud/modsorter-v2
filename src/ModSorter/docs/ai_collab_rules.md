## 1. AI 協働の固定ルール（厳守）

### コード提示の形式
1. 差し替え: 「差し替え対象の全文」→「差し替え後の全文」をセットで出す。
   既存コードの周辺に手が入る場合（既存行の修正、メソッド末尾への継ぎ足し、
   重複や構造崩れが起こりうる挿入など）は、たとえ「足すだけ」に見えても差し替え扱い。
   目印として数行だけ示すのではなく、差し替え対象の全文と差し替え後の全文を必ずペアで出す。
2. 追加: 既存コードを一切消さず純粋に足すだけのときに限り許可。
   その場合も「追加する直前の5行」は挿入位置の目印にすぎず、その5行の直後に丸ごと貼る
   ものと誤認されやすい。誤認の恐れがあるとき・周辺行に影響が及ぶときは 1（差し替え）を使う。
3. 新規ファイル: ディレクトリ・ファイル名・新規である旨を明記し、全文を出力する。
   → どこに何を入れる／消すかを毎回明確にするため。
   形式が守れていない場合は「固定ルール忘れてる」と指摘してよい。
4. 一度提示したコードを後から部分修正しない。
   提示後に「やはりここを直す」と追いの修正を足すのは禁止。修正が要ると分かった時点で、
   その修正を織り込んだ完成品を最初から1つだけ出す。
5. 記載途中で誤りに気づいたら、その場で記載を中止する。誤ったまま書き進めない・末尾に
   訂正を追記しない。まず謝罪し、正しい完成品を新たに作り直して出す。
6. 追加のときも「直前の5行」だけでなく「直後の5行」も必ず示し、挿入位置を一意に確定させる。
   閉じカッコ（}）が連続して位置が特定できない場合は、直前の実行文など特定できる手がかりを
   添えて一意に定める。前後5行の明示は毎回行い、省略しない。

### 応答スタイル
- 余計な前置き・繰り返しを減らし、要点を簡潔に。
- 前回までの内容を忘れて話すことを禁止。分からない場合は「分からない」と言う。
- 憶測での発言を禁止。判断に必要な現物が足りないときは、その現物を要求する。
- ユーザーへの命令・指示形を禁止。手順はユーザーが実行する前提で淡々と提示する。
- ユーザーに生成（実機テスト）を依頼するときは、テストに使う具体的なプロンプト文を必ず明記する。
  「生成して確認してください」だけで済ませず、ユーザーがそのままコピペして実行できる
  お題（例: 「クラッシングホイールで鉱石を粉砕」）を、ジャンル指定や空間サイズが要るなら
  それも添えて提示する。複数観点を確認したいときは観点ごとにプロンプトを分けて列挙する。
  プロンプト本体以外の余計な会話は足さない。
- 実機作業はユーザー側。AI はアプリを動かせない。AI の仕事はコードと判断の提示まで。
  結果（ログ・ブロックリスト）はユーザーが貼る。
- 「案A/案B」「修正1/修正2」等、ユーザーが指定していないラベル付け・区分け説明を挿入しない。
  何をどう変えるかを1種類ずつ「ここのこれをこうする」と端的に述べる。
- 「必ず遵守します」「確認してよいですか」等、作業を進めない前置き・許可求め・決意表明を書かない。
  確認が要る事項は質問せず自分で調べて確定し、結果を実装に漏れなく反映する。

### 検討プロセスの固定ルール（厳守）
判断ミス（プロンプトの定義漏れ・実機仕様との食い違い等）が過去に頻発したため、
回答を出す前に必ず次の3つを実施する。確認の往復はせず、完成品だけを出す。
1. 3回検討（必須）: 案を最低3通り（例: 完全自動／現状維持／安全側スコープ 等）出し、
   それぞれの利点・リスク・実機での破綻条件を比較してから1案に決める。
   ダメなら検討回数を増やすだけで、安易に往復確認へ逃げない。
2. ポンダー（実機挙動）チェック（必須）: Create 機械・ブロックを扱うときは、
   コードのプロンプト定義を信用せず、必ず実機の正しい挙動を確認してから判断する。
   一次情報の優先順は (a) 公式 Wiki（Creators-of-Create/Create の GitHub Wiki）→
   (b) Architect/Rules/*.txt の確定知見 → (c) 本ファイル「3. 確定知見」。
   ルールテキストやプロンプトが実機仕様と食い違っていたら、コードではなく実機を正とし、
   食い違い自体を修正対象として扱う（偽合格＝実機で動かないのに合格する状態を最優先で潰す）。
3. 現物調査と再現度の自己検証（必須）: 実在の構造物を生成する小分類は、寸法を当てずっぽうの
   比率で決めず、実物または復元船・実施例の主要目を先に調べ、出典と数値をコメントへ残す。
   全長・幅・高さの主要目だけで満足せず、各部の役割（人が入る／通る／載る／貫く）まで
   踏み込んで調べる。人が使う部分は人が使える寸法になっているかを必ず見る。
   そのうえで、コードが書いたとおりに出力されたかの確認で終わらせない。出力された形が
   実物に近いかを必ず考える。書いたコードから生成物の形を頭の中で組み立て、実物の写真・
   図面と突き合わせ、次を1つずつ確かめてから提示する。
   (a) 開口部（戸口・窓・昇降口）が実際に人の通れる幅と高さで開いているか。
       塞がっていないか、他の部材が正面に立っていないか。
   (b) 部材どうしが同じ座標を奪い合っていないか。柱・梁・マスト・階段が
       開口部や通路を貫いていないか。
   (c) 空中に浮くブロック・下から素通しになる床が出ないか。
   (d) 実物にある主要な部位が欠けていないか。実物に無い部位を足していないか。
   計算で確かめられるものは実際に数値を入れて確かめる（例: マスト位置の式へ全長を入れ、
   船楼の占める station と重ならないかを船種ごとに計算する）。
   ここで見つけた食い違いは、プリセットの初期値ではなく生成器の式の側を疑う。
   同じ不具合が複数の種類で同時に出ているときは、必ず生成器の側に原因がある。
- 上記3つを省いた回答は不可。守れていない場合は「3回検討/ポンダー/現物確認 忘れてる」と
  指摘してよい。

### コード参照ルール（厳守）
- 追加・差し替え・新規作成が発生する場合、該当箇所の現物は AI 自身が先に Git(raw) を
  参照して確認してから出す。
  raw 例: https://raw.githubusercontent.com/aonohayunoofficial-cloud/modsorter-v2/main/<パス>
- 呼び出し先・既存の同種メソッド・対応する UI 要素など関連実装も、憶測で書かず先に確認する。
- 既存に同じ機能のメソッドがあれば新規実装せず使い回す。
  （例: モデル一覧取得は `_architectHost.Generation.ListModelsAsync()` を使う）
- コミット・プッシュから次のコミット・プッシュまでは、ローカル（差し替え・追加済み）の内容を
  最新として進める。
- 呼び出し側だけを先に書いて実体（メソッド・型）を後回しにする等、コンパイルが通らない
  不整合な状態を作らない。呼び出しと実体は整合させてまとめて出す。

### プッシュ確認（厳守・コード出力の前提条件）
- コードを出す前に、対象ファイルと関連ファイルの raw を取得し、直前に提示した内容が
  リモートへ反映されているかを1件ずつ判定して結果を明示する。
  判定は「その提示で足したはずの識別子（プロパティ名・メソッド名・既定値）が raw にあるか」で行う。
- 判定結果が「未プッシュ」のファイルが1件でもあるときはコードを出さない。
  未プッシュの一覧と、プッシュ後に出す予定のファイル一覧だけを示して待機する。
  「ローカルを最新として進める」は、その差分がプッシュ済みだと確認できた範囲にのみ適用する。
- 未プッシュの状態で続けて別の変更を重ねると、リモートとローカルのどちらを基準に
  差し替え対象の全文を書いたのか判別できなくなる。これを不整合の発生源として扱う。
- ユーザーの実機結果（スクリーンショット・ログ）はローカル適用分の結果であり、
  プッシュ済みの証拠として扱わない。

### 1ファイルの容量（厳守）
- 1ファイルは 9,000 バイト（日本語コメント込みで概ね 250〜300 行）を目安とし、
  10,000 バイトを超えさせない。raw の1回の取得が 10,000 バイトで切れるため、
  超えた時点で AI が全文を確認できず、差し替え対象の全文を出せなくなる。
- 上限に近づいたら機能単位で partial へ分割する。命名は `<型名>.<役割>.cs`。
  （例: `HullExpander.Top.cs` / `HullExpander.Rig.cs` / `HullExpander.Castle.cs`）
- UI クラスは「パネル組み立て」と「既定値（プリセット）」を別ファイルへ分ける。
  船種・施設種が増えるたびに既定値が伸びるので、プリセット側だけが太る形にする。
- 分割の判断はコードを出す前に行う。上限を超える見込みのファイルへ足す提示はしない。
- ParamsControl 系の UI クラスは `Architect/Manual/` に置く。名前空間は
  `ModSorter.Architect.Manual` に揃え、フォルダと名前空間を一致させる。

### リポジトリ
- URL・raw URL はこのファイルに固定記載しない。再開時にユーザーが URL を送る。
  受け取るまで取得を試みず待機する。受領後、そこを基点に raw を取得して作業する。
- スタック: C#（.NET / WPF / fNbt）。Python は使わない。
